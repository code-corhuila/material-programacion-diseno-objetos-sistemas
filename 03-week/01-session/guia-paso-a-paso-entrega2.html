1 Definir e Implementar las Interfaces

Las interfaces definen contratos de comportamiento. Una interfaz dice "cualquier clase que me implemente DEBE tener estos métodos". Aplica el principio ISP dividiéndolas por responsabilidad.

📌 ¿Dónde creo las interfaces?

Crea un nuevo paquete com.biblioteca.interfaces. Cada interfaz va en su propio archivo .java dentro de ese paquete.

Ejemplo: Interfaces para el Sistema de Biblioteca Digital

Interfaz ¿Quién la implementa? Métodos que define Principio
Prestable Libro, Revista, Audiolibro prestar(), devolver() ISP
Descargable Libro, Audiolibro descargar(), getFormato() ISP
Notificable Clases de servicio de notificación enviarNotificacion(Usuario, String) DIP

Ejemplo: Interfaz Prestable.java

package com.biblioteca.interfaces;

/**
 * Contrato para recursos que pueden ser prestados.
 * Principio ISP: interfaz pequeña y específica.
 */
public interface Prestable {

    /**
     * Marca el recurso como prestado (no disponible).
     * @return true si el préstamo fue exitoso, false si no está disponible
     */
    boolean prestar();

    /**
     * Marca el recurso como devuelto (disponible nuevamente).
     */
    void devolver();
}

Ejemplo: Interfaz Descargable.java

package com.biblioteca.interfaces;

/**
 * Contrato para recursos que pueden descargarse digitalmente.
 * Principio ISP: separado de Prestable porque no todos los
 * recursos prestables son descargables (ej: revistas físicas).
 */
public interface Descargable {

    /**
     * Inicia la descarga del recurso.
     * @return URL o ruta del recurso descargado
     */
    String descargar();

    /**
     * Retorna el formato del archivo descargable.
     * @return formato (PDF, MP3, EPUB, etc.)
     */
    String getFormato();
}

Ejemplo: Interfaz Notificable.java

package com.biblioteca.interfaces;

import com.biblioteca.model.Usuario;

/**
 * Abstracción para el envío de notificaciones.
 * Principio DIP: las clases de alto nivel (servicios)
 * dependen de esta abstracción, no de una implementación concreta.
 */
public interface Notificable {

    /**
     * Envía una notificación a un usuario.
     * @param usuario destinatario
     * @param mensaje contenido de la notificación
     * @param tipo tipo de notificación (VENCIMIENTO, DISPONIBILIDAD, etc.)
     */
    void enviarNotificacion(Usuario usuario, String mensaje, String tipo);
}

💡 ¿Por qué separar las interfaces?

Si tuvieras una sola interfaz RecursoCompleto con todos los métodos, las clases que NO pueden descargarse (como una Revista física) estarían obligadas a implementar descargar() con un cuerpo vacío o lanzando una excepción. Eso viola el Principio de Segregación de Interfaces (ISP).

  • ✅ Correcto: Interfaces pequeñas → cada clase implementa solo lo que realmente puede hacer
  • ❌ Incorrecto: Una interfaz grande → clases con métodos vacíos o con throw new UnsupportedOperationException()

✅ Resultado del Paso 1

Tienes al menos 2 interfaces creadas en el paquete interfaces, cada una con sus métodos bien definidos y documentados. Las interfaces representan comportamientos específicos, no entidades.

2 Completar Herencia: Implementar Interfaces y Métodos Abstractos

Actualiza las clases concretas de la Entrega 1 para que implementen las interfaces y completen los métodos abstractos con lógica real.

Ejemplo: Libro.java actualizado — implementa Prestable y Descargable

package com.biblioteca.model;

import com.biblioteca.interfaces.Prestable;
import com.biblioteca.interfaces.Descargable;

/**
 * Libro: subclase de RecursoDigital.
 * Implementa Prestable (puede prestarse) y Descargable (tiene formato PDF/EPUB).
 *
 * Principio OCP: agregamos comportamiento implementando interfaces sin
 * modificar la clase padre RecursoDigital.
 *
 * Principio LSP: Libro puede sustituir a RecursoDigital en cualquier
 * contexto sin alterar el comportamiento esperado.
 */
public class Libro extends RecursoDigital implements Prestable, Descargable {

    private String isbn;
    private String autor;
    private int numeroPaginas;
    private String genero;
    private String formato;   // PDF, EPUB

    public Libro(int id, String titulo, int anioPublicacion,
                 String isbn, String autor, int numeroPaginas,
                 String genero, String formato) {
        super(id, titulo, anioPublicacion);
        this.isbn = isbn;
        this.autor = autor;
        this.numeroPaginas = numeroPaginas;
        this.genero = genero;
        this.formato = formato;
    }

    // ── Getters ──────────────────────────────────────────────────
    public String getIsbn()          { return isbn; }
    public String getAutor()         { return autor; }
    public int getNumeroPaginas()    { return numeroPaginas; }
    public String getGenero()        { return genero; }
    public void setGenero(String g)  { this.genero = g; }

    // ── Implementación de Prestable ───────────────────────────────
    @Override
    public boolean prestar() {
        if (!disponible) {
            System.out.println("El libro '" + titulo + "' no está disponible.");
            return false;
        }
        disponible = false;
        System.out.println("Libro '" + titulo + "' prestado exitosamente.");
        return true;
    }

    @Override
    public void devolver() {
        disponible = true;
        System.out.println("Libro '" + titulo + "' devuelto. Ya está disponible.");
    }

    // ── Implementación de Descargable ─────────────────────────────
    @Override
    public String descargar() {
        return "https://biblioteca.ejemplo.com/descargas/" + isbn + "." + formato.toLowerCase();
    }

    @Override
    public String getFormato() {
        return formato;
    }

    // ── Implementación del método abstracto de RecursoDigital ─────
    @Override
    public String mostrarInformacion() {
        return "[LIBRO] " + titulo +
               " | Autor: " + autor +
               " | ISBN: " + isbn +
               " | Páginas: " + numeroPaginas +
               " | Género: " + genero +
               " | Año: " + anioPublicacion +
               " | Formato: " + formato +
               " | Disponible: " + (disponible ? "Sí" : "No");
    }

    @Override
    public String toString() {
        return "Libro{isbn='" + isbn + "', autor='" + autor +
               "', titulo='" + titulo + "', paginas=" + numeroPaginas + '}';
    }
}

package com.biblioteca.model;

import com.biblioteca.interfaces.Prestable;

📌 Polimorfismo en acción

Gracias a la herencia y las interfaces, puedes escribir código genérico:

// Polimorfismo: RecursoDigital como tipo de referencia
RecursoDigital recurso = new Libro(...);
System.out.println(recurso.mostrarInformacion()); // llama la versión de Libro

// Polimorfismo con interfaz
Prestable prestable = new Revista(...);
prestable.prestar(); // llama la versión de Revista

// Lista polimórfica
List<RecursoDigital> catalogo = new ArrayList<>();
catalogo.add(new Libro(...));
catalogo.add(new Revista(...));
catalogo.add(new Audiolibro(...));
for (RecursoDigital r : catalogo) {
    System.out.println(r.mostrarInformacion()); // cada uno muestra su propia info
}

✅ Resultado del Paso 2

Todas las clases concretas implementan las interfaces correspondientes y el método abstracto mostrarInformacion() tiene lógica real en cada subclase. El código usa polimorfismo correctamente.

Paso 3 — Aplicar los Cinco Principios SOLID

Cada principio con ejemplo de código del proyecto Biblioteca Digital

S SRP — Single Responsibility Principle

Cada clase debe tener una única razón para cambiar.

❌ Violación de SRP — Clase con múltiples responsabilidades

// MAL: RecursoDigital gestiona el préstamo, la notificación y el guardado
public class RecursoDigital {
    public void prestar(Usuario u) { /* lógica de préstamo */ }
    public void enviarEmailVencimiento(Usuario u) { /* lógica de email */ }
    public void guardarEnBaseDatos() { /* lógica de persistencia */ }
}

✅ Aplicación correcta de SRP — Responsabilidades separadas

// BIEN: cada clase tiene UNA responsabilidad

// RecursoDigital: solo representa el recurso (modelo)
public abstract class RecursoDigital { ... }

// GestorPrestamos: solo gestiona la lógica de préstamos
public class GestorPrestamos {
    public Prestamo realizarPrestamo(Usuario u, RecursoDigital r) { ... }
    public void registrarDevolucion(Prestamo p) { ... }
}

// ServicioNotificacion: solo envía notificaciones
public class ServicioNotificacion implements Notificable {
    public void enviarNotificacion(Usuario u, String msg, String tipo) { ... }
}

// GestorCatalogo: solo gestiona el catálogo de recursos
public class GestorCatalogo {
    public void agregarRecurso(RecursoDigital r) { ... }
    public List<RecursoDigital> buscarPorTitulo(String titulo) { ... }
}

Justificación: Si cambia la lógica de notificaciones (por ejemplo, de email a SMS), solo modificamos ServicioNotificacion, sin tocar GestorPrestamos ni los modelos.

O OCP — Open/Closed Principle

Las clases deben estar abiertas para extensión, cerradas para modificación.

❌ Violación de OCP — Modificar código existente para agregar tipos

// MAL: cada vez que agregamos un tipo hay que modificar este método
public String obtenerDescripcion(RecursoDigital r) {
    if (r instanceof Libro) {
        return "Libro: " + ((Libro) r).getAutor();
    } else if (r instanceof Revista) {
        return "Revista: edición " + ((Revista) r).getNumeroEdicion();
    } else if (r instanceof Audiolibro) {
        return "Audio: " + ((Audiolibro) r).getNarrador();
    }
    // Si agrego Podcast, tengo que modificar este método → viola OCP
    return "";
}

✅ Aplicación correcta de OCP — Extensión mediante herencia

// BIEN: cada subclase implementa mostrarInformacion() de forma distinta.
// Si agrego un nuevo tipo (Podcast), solo creo la clase nueva SIN
// modificar ningún código existente.

public abstract class RecursoDigital {
    public abstract String mostrarInformacion(); // contrato
}

public class Libro extends RecursoDigital {
    @Override
    public String mostrarInformacion() { return "[LIBRO] " + titulo + "..."; }
}

public class Podcast extends RecursoDigital {  // nuevo tipo → solo nueva clase
    @Override
    public String mostrarInformacion() { return "[PODCAST] " + titulo + "..."; }
}

// El catálogo funciona sin cambios:
for (RecursoDigital r : catalogo) {
    System.out.println(r.mostrarInformacion()); // funciona para todos los tipos
}

Justificación: Agregar Podcast no requiere modificar GestorCatalogo, Main ni ninguna otra clase existente. El sistema está "cerrado para modificación" y "abierto para extensión".

L LSP — Liskov Substitution Principle

Los objetos de una subclase deben poder sustituir a los de la superclase sin alterar el comportamiento correcto.

❌ Violación de LSP — La subclase rompe el contrato del padre

// MAL: RecursoNoDisponible sobreescribe isDisponible() de forma inconsistente
public class RecursoNoDisponible extends RecursoDigital {
    @Override
    public boolean isDisponible() {
        throw new UnsupportedOperationException("No se puede consultar disponibilidad");
        // Cualquier código que espere un RecursoDigital se rompe aquí
    }
}

✅ Aplicación correcta de LSP — Subclases respetan el contrato

// BIEN: Libro, Revista y Audiolibro implementan prestar()/devolver()
// de forma coherente. El código que usa RecursoDigital funciona
// igual sin importar qué subclase concreta reciba.

public class GestorPrestamos {

    // Este método funciona con Libro, Revista o Audiolibro → LSP
    public Prestamo realizarPrestamo(Usuario usuario, RecursoDigital recurso) {
        if (!(recurso instanceof Prestable)) {
            System.out.println("Este recurso no es prestable.");
            return null;
        }
        Prestable prestable = (Prestable) recurso;
        boolean exitoso = prestable.prestar();
        if (exitoso) {
            return new Prestamo(generarId(), hoy(), null, "ACTIVO", usuario, recurso);
        }
        return null;
    }
}

Justificación: GestorPrestamos.realizarPrestamo() recibe cualquier RecursoDigital. Al llamar prestar() (vía interfaz Prestable), el comportamiento es correcto para Libro, Revista o Audiolibro. Ninguna subclase "rompe" el flujo.

I ISP — Interface Segregation Principle

Es mejor tener muchas interfaces pequeñas y específicas que una sola interfaz grande.

❌ Violación de ISP — Interfaz grande que fuerza métodos no aplicables

// MAL: una sola interfaz con todo
public interface RecursoCompleto {
    boolean prestar();
    void devolver();
    String descargar();       // Revista no puede descargarse → método vacío
    String getFormato();      // idem
    void reproducir();        // Solo audiolibros → vacío en Libro y Revista
}

// Resultado: Revista.java queda así (BAD):
public class Revista extends RecursoDigital implements RecursoCompleto {
    @Override
    public String descargar() { return null; }  // ← forzado, no tiene sentido
    @Override
    public void reproducir() { }                // ← forzado, vacío
}

✅ Aplicación correcta de ISP — Interfaces pequeñas por comportamiento

// BIEN: interfaces segregadas
public interface Prestable   { boolean prestar(); void devolver(); }
public interface Descargable { String descargar(); String getFormato(); }
public interface Reproducible { void reproducir(); int getDuracion(); }

// Libro implementa solo lo que puede hacer:
public class Libro extends RecursoDigital implements Prestable, Descargable { ... }

// Revista implementa solo préstamo:
public class Revista extends RecursoDigital implements Prestable { ... }

// Audiolibro puede prestarse, descargarse Y reproducirse:
public class Audiolibro extends RecursoDigital
        implements Prestable, Descargable, Reproducible { ... }

Justificación: Ninguna clase está forzada a implementar métodos que no le corresponden. El código es más limpio y las interfaces son reutilizables.

D DIP — Dependency Inversion Principle

Los módulos de alto nivel no deben depender de módulos de bajo nivel. Ambos deben depender de abstracciones.

❌ Violación de DIP — Dependencia directa de implementación concreta

// MAL: GestorPrestamos depende directamente de ServicioEmailNotificacion
public class GestorPrestamos {
    private ServicioEmailNotificacion emailService;  // implementación concreta

    public GestorPrestamos() {
        this.emailService = new ServicioEmailNotificacion(); // acoplamiento fuerte
    }
    // Si quiero cambiar a SMS, tengo que modificar GestorPrestamos
}

✅ Aplicación correcta de DIP — Depender de la abstracción

// Abstracción (interfaz)
public interface Notificable {
    void enviarNotificacion(Usuario usuario, String mensaje, String tipo);
}

// Implementaciones concretas
public class ServicioEmailNotificacion implements Notificable {
    @Override
    public void enviarNotificacion(Usuario u, String msg, String tipo) {
        System.out.println("[EMAIL] Para: " + u.getEmail() +
                           " | Tipo: " + tipo + " | Msg: " + msg);
    }
}

public class ServicioConsolaNotificacion implements Notificable {
    @Override
    public void enviarNotificacion(Usuario u, String msg, String tipo) {
        System.out.println("[CONSOLA] Usuario: " + u.getNombre() +
                           " → " + tipo + ": " + msg);
    }
}

// GestorPrestamos depende de la abstracción, no de una concreción
public class GestorPrestamos {
    private Notificable servicioNotificacion;  // abstracción

    // Inyección de dependencia por constructor
    public GestorPrestamos(Notificable servicioNotificacion) {
        this.servicioNotificacion = servicioNotificacion;
    }

    public Prestamo realizarPrestamo(Usuario usuario, RecursoDigital recurso) {
        Prestable prestable = (Prestable) recurso;
        boolean ok = prestable.prestar();
        if (ok) {
            Prestamo p = new Prestamo(1, "2026-05-01", "2026-05-15",
                                      "ACTIVO", usuario, recurso);
            servicioNotificacion.enviarNotificacion(usuario,
                "Préstamo de '" + recurso.getTitulo() + "' exitoso.",
                "PRESTAMO");
            return p;
        }
        return null;
    }
}

Justificación: En Main podemos elegir qué implementación de Notificable inyectar. Cambiar de email a consola no requiere modificar GestorPrestamos.

📌 Resumen: ¿Cómo demuestro SOLID en el README?

Para cada principio, el README debe incluir:

  1. Nombre del principio y explicación en 1-2 oraciones
  2. ¿Dónde se aplica? — nombre de la clase/interfaz en tu proyecto
  3. Fragmento de código real de tu implementación
  4. Justificación: ¿qué problema evita esta decisión de diseño?

4 Crear las Clases de Servicio (Lógica de Negocio)

Las clases de servicio implementan la lógica de negocio del sistema. Aplican el principio SRP: cada servicio se encarga de una sola área funcional.

📌 ¿Dónde creo los servicios?

Crea un paquete com.biblioteca.service. Cada clase de servicio va en su propio archivo dentro de ese paquete.

package com.biblioteca.service;

import com.biblioteca.model.RecursoDigital;
import java.util.ArrayList;
import java.util.List;

/**
 * Gestiona el catálogo de recursos de la biblioteca.
 * SRP: única responsabilidad → administrar el inventario de recursos.
 * OCP: funciona con cualquier subclase de RecursoDigital presente o futura.
 */
public class GestorCatalogo {

    private List<RecursoDigital> catalogo;

    public GestorCatalogo() {
        this.catalogo = new ArrayList<>();
    }

    public void agregarRecurso(RecursoDigital recurso) {
        catalogo.add(recurso);
        System.out.println("Recurso agregado: " + recurso.getTitulo());
    }

    public void mostrarCatalogo() {
        System.out.println("\n══ CATÁLOGO DE LA BIBLIOTECA ══");
        if (catalogo.isEmpty()) {
            System.out.println("El catálogo está vacío.");
            return;
        }
        for (RecursoDigital r : catalogo) {
            System.out.println(" • " + r.mostrarInformacion()); // Polimorfismo
        }
    }

    public List<RecursoDigital> buscarPorTitulo(String titulo) {
        List<RecursoDigital> resultados = new ArrayList<>();
        for (RecursoDigital r : catalogo) {
            if (r.getTitulo().toLowerCase().contains(titulo.toLowerCase())) {
                resultados.add(r);
            }
        }
        return resultados;
    }

    public List<RecursoDigital> listarDisponibles() {
        List<RecursoDigital> disponibles = new ArrayList<>();
        for (RecursoDigital r : catalogo) {
            if (r.isDisponible()) disponibles.add(r);
        }
        return disponibles;
    }

    public List<RecursoDigital> getCatalogo() {
        return catalogo;
    }
}

package com.biblioteca.service;

import com.biblioteca.interfaces.Notificable;
import com.biblioteca.interfaces.Prestable;
import com.biblioteca.model.Prestamo;
import com.biblioteca.model.RecursoDigital;
import com.biblioteca.model.Usuario;
import java.util.ArrayList;
import java.util.List;

/**
 * Gestiona los préstamos de recursos a usuarios.
 * SRP: única responsabilidad → ciclo de vida de préstamos.
 * DIP: depende de la abstracción Notificable, no de una implementación concreta.
 */
public class GestorPrestamos {

    private List<Prestamo> prestamos;
    private Notificable servicioNotificacion;
    private int contadorId;

    public GestorPrestamos(Notificable servicioNotificacion) {
        this.prestamos             = new ArrayList<>();
        this.servicioNotificacion  = servicioNotificacion;
        this.contadorId            = 1;
    }

    public Prestamo realizarPrestamo(Usuario usuario, RecursoDigital recurso,
                                     String fechaDevolucion) {
        if (!(recurso instanceof Prestable)) {
            System.out.println("El recurso '" + recurso.getTitulo() + "' no es prestable.");
            return null;
        }
        Prestable prestable = (Prestable) recurso;
        boolean exitoso = prestable.prestar();
        if (exitoso) {
            Prestamo p = new Prestamo(
                contadorId++, obtenerFechaHoy(), fechaDevolucion,
                "ACTIVO", usuario, recurso
            );
            prestamos.add(p);
            servicioNotificacion.enviarNotificacion(
                usuario,
                "Préstamo de '" + recurso.getTitulo() + "'. Devolver antes de: " + fechaDevolucion,
                "PRESTAMO"
            );
            return p;
        }
        return null;
    }

    public void registrarDevolucion(Prestamo prestamo) {
        if (!"ACTIVO".equals(prestamo.getEstado())) {
            System.out.println("El préstamo ya fue cerrado.");
            return;
        }
        Prestable prestable = (Prestable) prestamo.getRecurso();
        prestable.devolver();
        prestamo.setEstado("DEVUELTO");
        prestamo.setFechaDevolucion(obtenerFechaHoy());
        servicioNotificacion.enviarNotificacion(
            prestamo.getUsuario(),
            "Devolución de '" + prestamo.getRecurso().getTitulo() + "' registrada.",
            "DEVOLUCION"
        );
        System.out.println("Devolución registrada para préstamo #" + prestamo.getId());
    }

    public void mostrarPrestamoActivos() {
        System.out.println("\n══ PRÉSTAMOS ACTIVOS ══");
        boolean hayActivos = false;
        for (Prestamo p : prestamos) {
            if ("ACTIVO".equals(p.getEstado())) {
                System.out.println(" • " + p);
                hayActivos = true;
            }
        }
        if (!hayActivos) System.out.println("No hay préstamos activos.");
    }

    public List<Prestamo> getPrestamos() { return prestamos; }

    private String obtenerFechaHoy() {
        return java.time.LocalDate.now().toString();
    }
}

package com.biblioteca.service;

import com.biblioteca.interfaces.Notificable;
import com.biblioteca.model.Notificacion;
import com.biblioteca.model.Usuario;
import java.util.ArrayList;
import java.util.List;

/**
 * Implementación concreta del servicio de notificaciones.
 * DIP: implementa la abstracción Notificable, por lo tanto
 * puede ser sustituida por cualquier otra implementación
 * (email, SMS, push, etc.) sin cambiar GestorPrestamos.
 */
public class ServicioNotificacion implements Notificable {

    private List<Notificacion> historialNotificaciones;
    private int contadorId;

    public ServicioNotificacion() {
        this.historialNotificaciones = new ArrayList<>();
        this.contadorId = 1;
    }

    @Override
    public void enviarNotificacion(Usuario usuario, String mensaje, String tipo) {
        String fecha = java.time.LocalDate.now().toString();
        Notificacion notif = new Notificacion(contadorId++, mensaje, fecha, tipo, usuario);
        historialNotificaciones.add(notif);
        System.out.println("[NOTIFICACION → " + usuario.getNombre() + "] " +
                           tipo + ": " + mensaje);
    }

    public void mostrarHistorial() {
        System.out.println("\n══ HISTORIAL DE NOTIFICACIONES ══");
        for (Notificacion n : historialNotificaciones) {
            System.out.println(" • " + n);
        }
    }

    public List<Notificacion> getHistorial() {
        return historialNotificaciones;
    }
}

## ⚙️ Aplicación de Principios SOLID

### 🔴 S — Single Responsibility Principle
**¿Dónde se aplica?** Paquete `service`: cada clase tiene una única responsabilidad.
- `GestorCatalogo`: administra el inventario
- `GestorPrestamos`: gestiona el ciclo de préstamos
- `ServicioNotificacion`: envía notificaciones

**Código:**
```java
// GestorPrestamos solo gestiona préstamos.
// Si la lógica de notificaciones cambia, solo se modifica ServicioNotificacion.
public class GestorPrestamos {
    private Notificable servicioNotificacion; // abstracción, no implementación
    public Prestamo realizarPrestamo(Usuario u, RecursoDigital r, String fecha) { ... }
    public void registrarDevolucion(Prestamo p) { ... }
}
```

### 🟠 O — Open/Closed Principle
**¿Dónde se aplica?** `RecursoDigital` y sus subclases.
El sistema puede extenderse con nuevos tipos de recurso (Podcast, Ebook)
**sin modificar** `GestorCatalogo` ni `GestorPrestamos`.

**Código:**
```java
// Nueva extensión sin modificar código existente:
public class Podcast extends RecursoDigital implements Prestable {
    @Override
    public String mostrarInformacion() { return "[PODCAST] " + titulo; }
    @Override
    public boolean prestar() { ... }
    @Override
    public void devolver() { ... }
}
```

### 🟡 L — Liskov Substitution Principle
**¿Dónde se aplica?** `GestorPrestamos.realizarPrestamo()`.
Libro, Revista y Audiolibro son intercambiables como `RecursoDigital`.

**Código:**
```java
// funciona para Libro, Revista o Audiolibro → LSP
public Prestamo realizarPrestamo(Usuario u, RecursoDigital recurso, String fecha) {
    Prestable prestable = (Prestable) recurso;
    prestable.prestar(); // comportamiento correcto en cualquier subclase
}
```

### 🟢 I — Interface Segregation Principle
**¿Dónde se aplica?** Paquete `interfaces`: tres interfaces específicas.
- `Prestable`: solo para recursos que se prestan
- `Descargable`: solo para recursos con descarga digital
- `Notificable`: solo para servicios de notificación

**Código:**
```java
public class Revista extends RecursoDigital implements Prestable {
    // NO implementa Descargable porque las revistas no se descargan
}
```

### 🔵 D — Dependency Inversion Principle
**¿Dónde se aplica?** `GestorPrestamos` depende de `Notificable` (abstracción).

**Código:**
```java
// Constructor recibe la abstracción → fácil cambiar implementación
public GestorPrestamos(Notificable servicioNotificacion) {
    this.servicioNotificacion = servicioNotificacion;
}
// En Main se inyecta la implementación concreta:
Notificable notif = new ServicioNotificacion();
GestorPrestamos gp = new GestorPrestamos(notif);
```
